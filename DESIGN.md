# Wazuh all-in-one on Railway — design decisions (written before building)

## The cert/hostname problem — chosen approach

**Option (a) modified: deterministic deploy-time cert generation inside each service, no init container, no shared volumes.**

Why not the official `wazuh/wazuh-certs-generator:0.0.2` one-shot verbatim:
- The generator's `certs.yml` schema (`nodes.<type>[].name` + `.ip`) DOES accept arbitrary CNs/hosts,
  so the schema is not the blocker.
- The blocker is Railway topology: **Railway has no shared volumes between services** (one volume per
  service, not shareable) and no compose-style one-shot init container whose filesystem other
  services can read. Certs generated by one service cannot reach the other two.

Chosen mechanism: every service's wrapper Dockerfile bakes in a small Python script
(`wazuh_certs.py`, dep `cryptography`) that at boot derives the **same EC P-256 root CA
deterministically from a shared Railway secret** (`WAZUH_CA_SEED`, canonical on `wazuh-indexer`,
referenced by manager/dashboard via `${{wazuh-indexer.WAZUH_CA_SEED}}`):

- CA key scalar = int(SHA-512(seed|ca)) mod P-256 order; self-signed CA cert
  (CN=wazuh-railway-ca), fixed validity 2026-01-01 → 2049-01-01. KEYS are fully
  deterministic (byte-identical across services/restarts); cert signatures use
  randomized ECDSA nonces so cert BYTES differ per boot, but every instance's CA
  cert carries the same public key — chain validation (what TLS peers actually do)
  is identical everywhere. Verified locally with openssl (cross-CA leaf verification OK).

## Credentials — zero demo values

Canonical secrets (per-deploy `${{secret(n, charset)}}` expressions) live on `wazuh-indexer` and are
referenced cross-service (references survive into the published template; `secret(seed)` yields
different values per variable, so each secret is declared exactly once):

| Secret | Declared on | Consumed by |
|---|---|---|
| `WAZUH_CA_SEED` | wazuh-indexer | all three (cert derivation) |
| `INDEXER_PASSWORD` (admin user) | wazuh-indexer | indexer (internal_users.yml hash), manager (filebeat + wazuh-keystore), dashboard (opensearch auth) |
| `DASHBOARD_PASSWORD` (kibanaserver user) | wazuh-indexer | indexer (internal_users.yml hash), dashboard (keystore) |
| `API_PASSWORD` (wazuh-wui API user) | wazuh-indexer | manager (create_user.py), dashboard (wazuh.yml host entry) |

Non-secret literals are **code defaults** in the start scripts (`INDEXER_USERNAME=admin`,
`DASHBOARD_USERNAME=kibanaserver`, `API_USERNAME=wazuh-wui`, `API_PORT=55000`, SSL paths,
`FILEBEAT_SSL_VERIFICATION_MODE=full`, JVM `-Xms1g -Xmx1g`) so the published template needs
**zero deploy-form prompts**.

`internal_users.yml` is regenerated at indexer boot with bcrypt($2a$, cost 12) hashes of
`INDEXER_PASSWORD`/`DASHBOARD_PASSWORD`; the four unused demo users (kibanaro, logstash, readall,
snapshotrestore) are dropped — no known demo hash ships. Security index initializes from files via
`plugins.security.allow_default_init_securityindex: true` on the fresh data volume; later password
changes require wiping the indexer volume (documented seeding caveat).

## Services (project `wazuh-template`)

| Service | Image | Ports | Volume |
|---|---|---|---|
| `wazuh-manager` | wazuh/wazuh-manager:4.12.0 (+wrapper) | TCP proxies 1514 (agent report) + 1515 (enrol); API 55000 private-only | 1 × `/data`; wrapper symlinks the demo's PERMANENT_DATA dirs (`/var/ossec/{etc,logs,queue,api/configuration,...}`, `/etc/filebeat`, `/var/lib/filebeat`) into `/data` (Duplicati-style single-volume adaptation) |
| `wazuh-indexer` | wazuh/indexer:4.12.0 (+wrapper) | 9200 private-only, TLS | 1 × `/var/lib/wazuh-indexer` |
| `wazuh-dashboard` | wazuh/wazuh-dashboard:4.12.0 (+wrapper) | public domain → 5601, `server.ssl.enabled: false` (Railway edge terminates public TLS; internal hops stay TLS) | none (state lives in indexer) |
| `wazuh-agent` (throwaway verify only, removed before `templates create`) | wazuh/wazuh-agent:4.12.0 | — | none |

Wrapper flow per service: generate certs → write configs (opensearch.yml / internal_users.yml /
opensearch_dashboards.yml / ossec.conf from templates with Railway hostnames) → chown → drop to
image user via `chroot --userspec=1000:0` (indexer/dashboard) or `exec /init` (manager s6) → stock
entrypoint. ossec.conf is written directly to `/var/ossec/etc/ossec.conf` (no `/wazuh-config-mount`).

## Networking
- Manager: `INDEXER_URL=https://${{wazuh-indexer.RAILWAY_PRIVATE_DOMAIN}}:9200`; two TCP proxies
  (1514, 1515) for external agents (RAILWAY_TCP_PROXY_DOMAIN/PORT documented in README);
  `WAZUH_API_URL=https://${{wazuh-manager.RAILWAY_PRIVATE_DOMAIN}}` + API_PORT 55000 on dashboard.
- No UDP: syslog 514/udp impossible on Railway — documented in listing.
- No demo FQDNs remain anywhere; all hostnames come from Railway private DNS.

## Verification plan (zero-credential acceptance)
1. Fresh deploy → 3 services up; dashboard public URL serves login page.
2. Login `admin` / generated `INDEXER_PASSWORD` via browser.
3. Agent round-trip: `wazuh-agent` service enrolled against `wazuh-manager.railway.internal:1515`,
   reporting on 1514 → agent Active in dashboard/API; `wazuh-alerts-*` searchable on indexer REST
   with admin creds over TLS (proves the full cert chain); plus raw TCP probe of both public proxies.
4. Restart all three (kill PID 1 via `railway ssh`) → cert public keys identical
   (fingerprints), client.keys + alerts persist, agent rejoins.
5. Delete agent service → connect repo sources → template draft → audit serializedConfig (no
   literal values captured) → publish → 2/2 fresh template deploys reach login + agent events →
   delete both throwaway verify projects (projectDelete GraphQL).

## Known risks / mitigations
- Indexer JVM boot is slow (~1–3 min): no public healthcheck on indexer (private-only), dashboard
  crash-loops until indexer is up (restartPolicy ON_FAILURE) — acceptable.
- Amazonlinux 2023 images: python3 + pip cryptography/bcrypt wheels installed at build (x86_64).
- Ed25519 rejected (Java <15 lacks EdDSA); ECDSA P-256 is supported by Java/Go/Node alike.
- OpenSearch dashboards `server.ssl` disabled — deviation from compose demo (Railway edge serves
  public TLS; backend HTTP). Documented in listing.
